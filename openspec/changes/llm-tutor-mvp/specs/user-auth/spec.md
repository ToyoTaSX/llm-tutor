# Spec Delta

## Purpose

Даёт пользователям регистрироваться и входить по логину и паролю. Разделяет студентов и лекторов, чтобы функции управления лекциями и статистики были доступны только лекторам.

## ADDED Requirements

### Requirement: Регистрация по логину и паролю
Система SHALL позволять любому посетителю создать учётную запись, указав уникальный логин и пароль. Логин нормализуется: пробелы по краям обрезаются, регистр не учитывается. Длина логина 3–32 символа (латиница, цифры, `_`, `.`, `-`), пароля не меньше 6 символов.

#### Scenario: Успешная регистрация
- **WHEN** посетитель отправляет форму регистрации со свободным логином `student1` и паролем длиной 8 символов
- **THEN** система создаёт учётную запись и сразу выполняет вход под ней

#### Scenario: Логин уже занят
- **WHEN** посетитель регистрирует логин ` Student1 `, а учётная запись `student1` уже существует
- **THEN** система отклоняет регистрацию с сообщением «Логин уже занят»

#### Scenario: Некорректные данные
- **WHEN** посетитель указывает пароль из 4 символов или логин с недопустимыми символами
- **THEN** система отклоняет регистрацию и показывает, какое поле неверно

### Requirement: Хранение паролей
Система MUST хранить пароли только в виде криптостойкого хеша с солью и никогда не возвращать пароль или хеш в ответах API.

#### Scenario: Пароль не хранится открытым текстом
- **WHEN** пользователь зарегистрирован с паролем `secret123`
- **THEN** в базе данных нет строки `secret123`, а API профиля не содержит ни пароля, ни хеша

### Requirement: Вход и сессия
Система SHALL выполнять вход по паре логин–пароль и выдавать сессию ограниченного срока действия (по умолчанию 24 часа). Сессия сохраняется после перезагрузки страницы.

#### Scenario: Успешный вход
- **WHEN** пользователь вводит верные логин и пароль
- **THEN** система открывает интерфейс, соответствующий его роли

#### Scenario: Неверные учётные данные
- **WHEN** пользователь вводит неверный пароль или несуществующий логин
- **THEN** система отказывает во входе с одинаковым сообщением «Неверный логин или пароль» в обоих случаях

#### Scenario: Сессия истекла
- **WHEN** срок сессии истёк и пользователь выполняет любое действие
- **THEN** система перенаправляет его на страницу входа

#### Scenario: Выход
- **WHEN** пользователь нажимает «Выйти»
- **THEN** сессия завершается и открывается страница входа

### Requirement: Роль лектора из конфигурации
Система SHALL определять роль при каждом входе: пользователь с логином из списка `LECTURER_LOGINS` (через запятую, без учёта регистра и пробелов) получает роль «лектор», остальные — «студент». Роль не хранится в базе, пароли лекторов в конфигурации не задаются.

#### Scenario: Лектор регистрируется сам
- **WHEN** `LECTURER_LOGINS=ivanov,petrova` и посетитель регистрирует логин `Ivanov`
- **THEN** после входа он получает роль «лектор» и видит разделы «Документы» и «Статистика»

#### Scenario: Изменение списка лекторов
- **WHEN** логин `petrova` удалён из `LECTURER_LOGINS` и система перезапущена
- **THEN** при следующем входе `petrova` получает роль «студент»

### Requirement: Контроль доступа по роли
Система MUST проверять роль на сервере для каждой операции лектора: управление документами и статистика. Скрытия элементов интерфейса недостаточно.

#### Scenario: Студент обращается к API лектора
- **WHEN** пользователь с ролью «студент» напрямую вызывает операцию загрузки документа или получения статистики
- **THEN** система отклоняет запрос с ошибкой «доступ запрещён» и ничего не изменяет

#### Scenario: Запрос без сессии
- **WHEN** запрос к любой операции, кроме регистрации и входа, приходит без действующей сессии
- **THEN** система отклоняет его как неавторизованный

### Requirement: Лектор может задавать вопросы
Система SHALL давать лектору тот же интерфейс вопросов и ответов, что и студенту, вместе с разделами лектора.

#### Scenario: Лектор проверяет ассистента
- **WHEN** лектор открывает раздел «Чат» и задаёт вопрос
- **THEN** он получает ответ с источниками так же, как студент
